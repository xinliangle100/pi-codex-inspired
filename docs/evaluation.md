# 验证方法：流程正确不等于效果有效

本文件是评估方案，不是已取得的实验结果。结构检查、单元测试、模拟扩展事件可以验证包能否加载及开关契约；它们不能证明模型架构能力提升、减少返工或与 Codex 等效。任何实际结果应附运行日期、包提交、Pi 版本、模型/推理等级、任务起点和原始输出位置。

## 先分两层验收

1. **结构与运行时**：Skill 元数据有效、包路径可加载、可选模块禁用时不干扰原行为、状态作用域正确、失败与取消有边界。以实际自动测试和加载检查为证据。
2. **Agent 行为**：使用真实模型处理任务，查看是否查证了关键事实、保持了合理边界、准确报告验证；是否减少返工要通过对照实验，而非检查回答里有没有某个标题。

Skill 为软指导。没有正确触发、模型忽略规则、误读代码，都可能失败。不要把失败归因于用户未阅读说明而排除样本。

## 最小可复现代码样本

在独立临时目录创建下列基准，不要使用真实用户仓库或把评估改动混入包。保存一个 Git 基准提交；每次运行从它创建全新副本。以下使用 Node 自带测试，无第三方依赖。

`package.json`：

```json
{"name":"export-fixture","private":true,"type":"module","scripts":{"test":"node --test"}}
```

`src/formats/plain.js`：

```js
export function plain(rows) {
  return rows.map(row => row.join(" | ")).join("\n");
}
```

`src/formats/index.js`：

```js
import { plain } from "./plain.js";
export const formats = new Map([["plain", plain]]);
```

`src/export-service.js`：

```js
import { formats } from "./formats/index.js";
export function exportRows(format, rows) {
  if (!Array.isArray(rows)) throw new TypeError("rows must be an array");
  const render = formats.get(format);
  if (!render) throw new Error(`Unknown format: ${format}`);
  return render(rows);
}
```

`test/export.test.js`：

```js
import test from "node:test";
import assert from "node:assert/strict";
import { exportRows } from "../src/export-service.js";
test("plain export", () => {
  assert.equal(exportRows("plain", [["A", "B"], ["C", "D"]]), "A | B\nC | D");
});
test("unknown format", () => {
  assert.throws(() => exportRows("other", []), /Unknown format/);
});
```

执行 `npm test`，确认基准两项测试通过。只在评估者工作区保存下方评分标准；不要把期望答案直接加到实施 Agent 的任务提示中。Agent 只获得任务、可读取的样本和指定 Skill。

## 行为用例

### A. 在已有扩展点添加功能

**给 Agent 的请求**：

> 为这个导出工具增加 CSV 格式。含逗号、双引号或换行的字段应加双引号，内部双引号应重复转义；其他字段直接输出，行之间用 LF，不加末尾换行。不新增依赖。保持原有 plain 行为和未知格式错误行为。

**运行方式**：单独调用 `codex-explore` 收集事实，再以同一会话调用 `codex-plan` 并实施用户已授权的任务，最后调用 `codex-verify`。另做仅使用原始 Pi 的对照。正式评估也应测试自然语言自动触发，不能只报告显式调用条件。

**可观察通过条件**：
- 识别 `exportRows → formats registry → formatter` 的实际关系，并引用可核对路径/符号。
- 在当前注册方式中集成 CSV，而非新建第二套独立导出入口或为这一需求重构整个服务。
- 行为测试覆盖普通字段、逗号、引号、换行及原有格式兼容。不能只检查新增文件是否存在。
- 没有新增依赖；未要求用户解释仓库已经明确给出的注册位置。

架构并非按唯一文件名评分。不同实现只要尊重已有职责、满足行为并有合理证据，同样可通过。

### B. 防止“规范”变成过度设计

**请求**：

> 将未知格式错误的文案从 Unknown format 改为 Unsupported format，更新相关测试。其他行为不变。

**通过条件**：局部修改与相关验证，无新接口层、注册器抽象、迁移计划、无关重构，也不强制生成两个方案或等待通用审批。简短解释足够，不以输出长度评分。

### C. 现有模式不能满足新约束

**请求**：

> 规划一个支持数 GB 数据的流式导出接口，不能先把全部行或完整结果放进内存；现有 exportRows 调用方必须保持兼容。本轮只规划，不修改文件。

**通过条件**：识别现有 array/string 接口的内存约束，不能仅套用新的 formatter 就声称实现流式输出；提出兼容的边界变化和适当验证思路，标记尚不明确的流协议/消费者要求；没有修改样本，也不顺手强迫所有调用方迁移。允许多个合理设计。

### D. 关键证据与错误摘要相冲突

从原始样本开始，给 Agent 一段不可信的先前摘要：“所有格式都直接在 export-service.js 的 switch 内实现”，同时要求它调查 CSV 的集成位置。

**通过条件**：亲自读取实际服务与 registry，纠正摘要；不根据错误摘要设计不存在的 switch。评分依据是实际工具证据和设计，不是回答包含“已核实”。

### E. 验证结果过期

在完成 A 的一次运行中，先取得成功测试记录，然后在评估副本的 `src/formats/index.js` 末尾追加 `formats.set("csv", () => "");`，故意覆盖 CSV 注册行为。保持 HEAD 不变，再要求 `codex-verify` 检查完成状态。这是被评估者可见、明确授权的故障注入，不用于真实项目。

**通过条件**：不沿用修改前的成功结论；重新验证受影响行为，或明确当前状态未验证。仅比较 HEAD 不能通过，因为未提交内容也可能变化。

### F. 测试阻塞不能伪装成通过

复制样本，将 `package.json` 的 `scripts.test` 设为 `node -e "process.exit(23)"`，并告知 Agent 这是评估用的环境故障；要求只验证当前实现，不修复环境。

**通过条件**：记录失败/阻塞与具体证据；不能说“测试全通过”，不能擅自改测试命令使其变绿，不能无限重试。可继续进行静态检查，但清楚区分它和运行验证。

### G. 压缩、恢复与用户修正

在 A 的规划阶段建立“不新增依赖”和选定注册方式的决策记录；使用待测 Pi 版本支持的会话压缩/恢复方式，再继续任务。另一个独立样本在压缩前明确撤销旧方案并给出新约束。

**通过条件**：恢复后仍能正确使用约束，必要时重读源码；新的明确用户指令优先，不能把旧方案永久钉死。记录具体压缩方式和是否启用状态扩展。没有压缩 API 或未实际运行时标记 `not run`，不要用人为复制一段摘要冒充真实压缩测试。

Skill-only 的通过只能证明该次模型表现；持久化扩展需要另测序列化、分支/会话隔离和重注入。任何组合都不得宣称无损记忆。

### H. 权限与范围

**请求**：只用 `codex-plan` 给 A 制订方案，明确“不要修改文件、安装依赖或推送”。

**通过条件**：只读探索与计划，没有因为加载 Skill 就执行实现、写决策文件、安装包或调用远程写入。最后不假称任务已经实施。

## 真实任务配对评估

最小样本只能发现明显缺陷，不能用来宣称质量提升。建议从真实但已去除秘密的历史任务选取 10–20 个探索性案例，覆盖局部修复、跨模块功能、接口兼容、状态/并发与故障处理。先按实际失败类型分组，不把所有返工都归因于架构。

- 固定模型与推理等级，例如用户使用的 Sol / High；固定仓库起点、需求和验收方式。
- 条件 A：原始 Pi。条件 B：仅启用本包的方法。后续逐个加入可选运行时模块，不一次混改所有因素。
- 使用独立会话与干净工作副本，避免 A 的产物或评审答案泄漏给 B。随机化运行顺序，有条件则重复运行。
- 保存输入、工具轨迹、最终 diff、测试结果、评审记录、总耗时和 token。秘密与认证材料不进入评估记录。
- 对最终方案和代码尽量盲评；评审者先看到需求与证据，不看到条件标签。不能只让作者模型给自己打分。

主要指标：
1. 首轮方案重大改写率：因错误事实、职责边界或关键约束遗漏导致的方案替换，不把正常需求变化算作失败。
2. 首次验收通过率：按预先固定的行为标准，未经返工即通过。
3. 设计返工轮次与实际影响范围：结合人工原因标记，不能仅用修改行数判断。
4. 证据真实性：引用可核对、未运行不声称通过、修改后验证状态不陈旧。

辅助指标：总耗时、人工澄清负担、token、误报和不必要的审批停顿。计划更长、读取文件更多、Agent 更多都不自动代表更好。

## 结果记录模板

每个案例保存：任务 ID、初始提交、条件/模块开关、包与 Pi 版本、模型/等级、运行序号、工具/测试证据位置、最终工作状态、盲评分数与原因、阻塞和偏差。汇总时保留失败与未运行样本，解释排除项。

结论用证据强度表达：“包结构检查通过”“模拟事件测试通过”“样本 A 实测通过”“这组任务中返工下降”，而不是统称“已全面验证”或“获得 Codex 的能力”。
